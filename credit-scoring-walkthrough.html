Reading the ledger: the Kitu ML Service

Kitu ML Service (v2.0.0) reads a business's mobile-money transaction history, turns it into a credit score, forecasts the next two weeks of cash flow, maps who the business trades with, and writes it all up as a lender-ready report. In one sentence, it answers: can this business repay a loan?

Framework FastAPI
Model version v0.2-seasonal-network-shap
Endpoints 9

A worked example carried through this walkthrough: a repayment likelihood of 86.2% becomes a final score of 862, which clears the 800 threshold for an A.

01 Imports

fastapi builds the web API — every function wearing an @app.get(...) decorator becomes a callable endpoint, like GET /score/15. sqlalchemy connects to the database directly, so the service reads live transactions from MySQL or Postgres rather than static CSVs. pandas turns the transaction table into a DataFrame for analysis, and numpy handles the numerical work underneath it.

networkx builds a graph of who trades with whom — business, counterparties, and the links between them. shap is imported for model explainability, but it's worth flagging early: the real SHAP library is never actually called. The code computes its own simplified, SHAP-like contribution values by hand instead. GradientBoostingRegressor from scikit-learn is the one genuine trained model in the service, used later for cash-flow forecasting. reportlab handles PDF report generation.

02 Creating the API

app = FastAPI(title="Kitu ML Service", version="2.0.0")

This single line creates the web application and names it. Every subsequent @app.get(...) decorated function hangs off this object as a route — including two housekeeping ones:

GET / GET /health

The root returns a one-line status string; /health reports service name and the current MODEL_VERSION — useful for uptime checks and confirming which scoring logic is live.

Rather than scattering version numbers across the codebase, the API surfaces this one string in its responses so a client always knows which scoring logic produced a given result.

05 Tanzanian seasonal calendar

One of the more distinctive design choices in the service.

Instead of treating every day as identical, TANZANIAN_SEASONS encodes the rhythm of local economic life: salary days, Ramadan, harvest season, and weekly market days. Each period shifts how much weight a business's activity should carry.

Salary week
More cash in → higher sales → lower risk
Harvest season
Farmers earn → shops sell more → healthier books

The calendar itself is a plain dictionary — salary days run from the 25th through the 4th, Ramadan is approximated to two months since it shifts yearly, harvest covers the long-rains and short-rains windows, and market days are set to Monday and Thursday.

08 Feature engineering

The heart of the scoring pipeline — where raw transactions become the measurements the score is built from.

def engineer_features(df):
    ...

Models don't consume raw transaction rows well; they need summarized signals. This function produces four of them.

Transaction frequency

active_days / total_days. A business observed for 30 days that traded on 24 of them scores 24/30 = 80. Businesses that show up regularly read as healthier.

Cash flow stability

For each day, net flow is incoming − outgoing. The code measures how consistent that daily net is using the coefficient of variation:

CV = standard_deviation / abs(mean)
PatternDay 1Day 2Day 3Reading
Stable1,0009001,100low CV → high score
Volatile10,000−5,0008,000high CV → penalized

The final score is 100 − penalty, so lower volatility earns a higher score.

Seasonal score

Every transaction date is stamped with its multiplier from Section 06 (1.0, 1.5, 1.65, and so on), and the mean across all transactions becomes the seasonal alignment score — businesses active during favorable periods score higher here.

Network health

Counts unique counterparties. A business trading with a single person reads as fragile; one trading with 75 reads as resilient. Roughly ten or more unique counterparties maps to the maximum score of 100.

Repayment likelihood

The four scores above are combined as a fixed weighted average — not a trained model:

FactorWeight
Cash flow stability35%

Seasonal alignment15%

09 The /score endpoint

GET /score/{business_id}

Ties everything together: load transactions → engineer features → compute contributions → produce the final score → assign a grade.

SHAP-like values

Rather than calling the imported SHAP library, the endpoint approximates feature importance by hand:

shap_values = {
    k: round((factors[k] / 100) * weight * 1000, 2)
    for k, weight in feature_weights.items()
}

Each factor score is normalized to 0–1, multiplied by its weight, then scaled onto the same 0–1000 range as the final score. A cash-flow stability score of 90 at its 35% weight contributes (90/100) × 0.35 × 1000 = 315 — so the four contributions read on the same scale as the score itself, rather than as small percentage points.

Final score and grade

score = repayment_likelihood * 10  # clamped to 0–1000

A repayment likelihood of 86.2% becomes a score of 862, matching the gauge at the top of this page.

10 /network

GET /network/{business_id}

Builds a directed graph with NetworkX — edges point from counterparty to business for incoming money, and business to counterparty for outgoing. From that graph it reads off in-degree and out-degree for the business, then adds three more views: the top 5 counterparties by transaction volume, "loyal" counterparties defined as anyone with 3 or more transactions, and a network health score of (unique counterparties / 10) × 100, capped at 100 — the same formula used inside the score itself.

11 /forecast

GET /forecast/{business_id}

The one endpoint backed by a genuinely trained model rather than hand-built rules.

The endpoint first checks there's enough history — fewer than 7 days of transactions returns a 422 rather than a forecast. Otherwise transactions are aggregated into daily net cash flow, each day gets three features — day of week, day of month, and the seasonal multiplier — and a GradientBoostingRegressor (100 estimators) is trained on the spot:

X = daily[["dow", "dom", "seasonal"]]
y = daily["net_flow"]
model.fit(X, y)

predictions = model.predict(forecast_features)  # next 14 days

The response returns the day-by-day forecast plus a summary of whether the outlook is positive or negative.

12 /repayment-outcome

POST /repayment-outcome

Lets a lender (MFI) report back what actually happened after a loan. The request body must include business_id, loan_amount, outcome, and lender_id — missing any of them returns a 422, as does an outcome outside on_time, late, or default. Valid submissions are logged to the audit_logs table. Nothing retrains automatically, but it's laying down the labeled dataset a real supervised model would eventually need.

13 /report

GET /report/{business_id}

Loads the transaction data, calculates the score, and builds a styled PDF via ReportLab, branded "Kitu Analytics — Credit Intelligence Report" in navy and green. It lays out four sections in order — a credit score summary table, the factor breakdown with each contribution, a financial summary in TZS, and a disclaimer noting the report isn't financial advice — then streams the file back as kitu_credit_report_{business_id}.pdf.

14 /bot-compliance

GET /bot-compliance/{business_id}

A regulator-facing report for Bank of Tanzania review, versioned as BoT_compliance_v1. It states the score and which factors produced it, confirms no protected attributes were used, notes data residency (Johannesburg, ZA on DigitalOcean), and confirms consent was verified under the PDPA 2022 framework. Fairness indicators include an appeal mechanism and bilingual explanations (English and Swahili), and the regulatory notes cover the right to withdraw consent, immutable audit logging, and a 48-hour SLA on appeals.

16 Strengths and gaps

+ Strengths

  • Clean separation between data loading, feature engineering, and endpoints
  • Effective use of pandas for transaction analysis
  • Built-in explainability via feature contributions
  • Scoring, forecasting, network analysis, and reporting from one API
  • Professional, lender-ready PDF output

! Areas to improve

  • The imported shap library is never used — contributions are hand-approximated instead
  • The score is a fixed weighted formula, not a trained model — repayment outcomes already being logged could train one
  • The forecasting model retrains on every request; training offline and serving a saved model would scale better
  • Features could grow to include rolling averages, amount trends over time, and fraud indicators
Bottom line — A solid foundation for a mobile-money credit-scoring platform, combining business rules, feature engineering, graph analysis, real forecasting, and reporting in one service. The clearest next step is moving from the current rule-based score to a model trained on real repayment outcomes as they accumulate.
